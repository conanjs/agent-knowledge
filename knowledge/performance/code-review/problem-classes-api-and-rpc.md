# Performance problem classes for code review: API and RPC design

## Summary
**TL;DR:** Most API performance problems are already classes elsewhere (N+1 calls, overfetching, unbounded input, slow work inline, missing caching). Three shapes are specific to RPC (remote procedure call) design and pass the admission test: one HTTP/2 connection whose stream limit queues calls, gRPC connections pinned to one backend by a connection-level balancer, and whole datasets in one unary message. Two more were considered and not admitted (a flow-control window too small for large messages, a chain of synchronous calls between services); their sourced facts sit in Lookup notes. Each has a signal in code or config, a named fix, and a count you can state before running anything. The long "Belongs to an existing class" list gives the API-specific signal for the rest of the API findings.
**Use this when:** you review gRPC client or server setup, `.proto` files, GraphQL schemas and resolvers, REST (Representational State Transfer) handlers, Kubernetes Service manifests for RPC backends, or a handler that calls other services.
**Not this doc:** the first 39 classes (`io-batching-n-plus-one`, `payload-overfetch`, `unbounded-input`, `distributed-calls`, `inline-slow-work`, `connection-management`) → [problem-classes.md](problem-classes.md); HTTP caching, compression and HTTP/1.1 connection count → [problem-classes-network-and-delivery.md](problem-classes-network-and-delivery.md); broker payloads → [problem-classes-messaging-and-jobs.md](problem-classes-messaging-and-jobs.md); gRPC keepalive and dead connections → [../../grpc/stale-connection-keepalive.md](../../grpc/stale-connection-keepalive.md); the review agent → [perf-reviewer-calibration.md](perf-reviewer-calibration.md).

## Scope
**Domain:** API and RPC design visible in handlers, schemas and interface definitions: gRPC channels, messages and load balancing; GraphQL schemas and resolvers; REST list, batch and long-running methods; synchronous calls between services. Covered products: gRPC as documented on grpc.io, grpc-go v1.85.0, grpc-java 1.86.0, gRPC for .NET and Kestrel in the ASP.NET Core 11.0 docs, Kubernetes Services, GraphQL with Hot Chocolate v15 as the example server. Not covered: API security beyond cost limits, schema versioning, service-mesh tuning, Protocol Buffers encoding internals.

**Notation** (each symbol with one worked example):
- **c**: concurrent calls a client has in flight to one target. Example: 400 request threads each waiting on one gRPC call gives c = 400.
- **s**: the server's concurrent-stream limit per HTTP/2 connection. Example: with s = 100 and c = 400 on one connection, 400 − 100 = 300 calls wait in the client queue.
- **k**: backend instances (pods) behind one service name. Example: k = 6 pods; with every call on one pinned connection, 1 pod works and 5 are idle.
- **b**: bytes in one message. Example: an export of 200,000 rows at 500 bytes each is b = 100 MB, 25 times a 4 MB receive limit.
- **w** and **RTT**: flow-control window in bytes and round-trip time. Example: w = 768 KiB and RTT = 100 ms allow at most 768 KiB per 100 ms, about 7.5 MiB per second on one stream.
- **d** and **t**: synchronous hops in a call chain, and the time one hop takes. Example: gateway → orders → pricing → stock is d = 3 hops after the gateway; at t = 20 ms each, the chain adds 3 × 20 = 60 ms before the gateway can answer.

| Term | Plain meaning | Analogy | Concrete example |
|---|---|---|---|
| Channel (gRPC) | A client-side object that owns connections to one target and reuses them for calls | A phone line kept open to one office | `grpc.NewClient("dns:///orders:50051")` shared by all request handlers |
| Stream (HTTP/2) | One request/response exchange multiplexed on a connection; each gRPC call is one stream | One conversation on a party line | 100 unary calls in flight are 100 streams on one connection |
| Unary vs streaming RPC | Unary: one request, one response. Streaming: a sequence of messages on one call | A letter vs a phone call | `rpc Get(Req) returns (Resp)` vs `rpc Export(Req) returns (stream Chunk)` |
| L4 and L7 load balancer | L4 (transport) spreads TCP connections; L7 (application) spreads individual HTTP requests | A doorman who assigns you a table vs a waiter who sends each order to any cook | Kubernetes ClusterIP Service (L4) vs Envoy (L7) |
| Pick first / round robin | gRPC client policies: use the first address that connects, or rotate over all | Always calling the first number in the list vs rotating through the list | `pick_first` (default) vs `round_robin` in the service config |
| Flow-control window | Bytes a receiver lets the sender send before it must wait for a window update | A loading dock with room for a fixed number of pallets | Kestrel stream window 768 KiB by default |
| Long-running operation (LRO) | A method that returns a status resource at once and finishes the work later | A dry-cleaning ticket | `202 Accepted` with `Operation-Location: /operations/123` |
| Field mask / view | A request option that names which fields the response should contain | Ordering a dish without the sides | `view=BASIC` on a List method |

## Catalog

**Channels and connections (gRPC over HTTP/2)**

| Class | Signals in code | Fix | Before → after | Check |
|---|---|---|---|---|
| `single-connection-stream-cap` | One process-wide gRPC channel or client singleton that carries both high-concurrency unary calls and long-lived streams (`Watch`, `Subscribe`); a custom .NET `SocketsHttpHandler` passed to `GrpcChannel` with no `EnableMultipleHttp2Connections = true`; Kestrel `Http2.MaxStreamsPerConnection` raised to "fix" queueing; a server option such as grpc-go `MaxConcurrentStreams(n)` set low | grpc.io: a separate channel for each area of high load, or a pool of channels with distinct channel args; .NET 5+: `EnableMultipleHttp2Connections = true`; put long-lived streams on their own channel | Calls sent at once per connection: capped at s, with c − s waiting in the client → about c / s connections, no queue (arithmetic). Each connection usually has a concurrent-stream limit, and at the limit additional RPCs are queued in the client and wait for active ones to finish ✅[^grpc-perf]; high load or long-lived streaming RPCs might see performance issues from this queueing ✅[^grpc-perf]; most servers set the limit to 100 by default, per Microsoft's gRPC for .NET page ✅[^ms-grpc-perf]; Kestrel `MaxStreamsPerConnection` defaults to 100 and refuses excess streams (ASP.NET Core 2.2 to 11.0) ✅[^kestrel-streams]; RFC 9113 sets no initial limit and recommends a value no smaller than 100 ✅[^rfc9113]; in .NET 5+, a `GrpcChannel`'s internal handler is configured automatically to open extra connections at the limit ✅[^ms-grpc-perf] | Client metric: calls in flight per connection against s; time from call start to request headers sent; a load test at c = 2·s shows queue time before the fix and none after |
| `rpc-connection-pinning` | A gRPC client that targets a Kubernetes ClusterIP Service name (`orders:50051`) or a network load balancer; a `dns:///` target with no `loadBalancingConfig` in the service config; a .NET `GrpcChannel.ForAddress("dns:///…")` with no `RoundRobinConfig`; one pod hot while scaling out does not help | Client-side `round_robin` over a headless Service (`clusterIP: None`) with a `dns:///` target; or an L7 proxy (Envoy, Linkerd, YARP) that spreads calls | Backends doing one client's calls 1 → k. L4 load balancers work at the connection level and so do not work well with gRPC: all calls over a connection go to one endpoint ✅[^ms-grpc-perf]; with a network load balancer the other servers are idle, and Kubernetes by default uses a network load balancer between pods ✅[^ms-grpc-lb]; grpc.io says that by default the `pick_first` policy is used, which does no load balancing, while `round_robin` rotates over all connected backends for each RPC ✅[^grpc-lb] (the page names no language); in grpc-java 1.86.0, if `ManagedChannelBuilder.defaultLoadBalancingPolicy` is not set, the default is `pick_first` ✅[^grpc-java]; in .NET, a channel with no service config, or one with no load balancer in it, defaults to `PickFirstLoadBalancerFactory` ✅[^ms-grpc-lb]; for a headless Service, kube-proxy does no load balancing and DNS returns the Pods' addresses ✅[^k8s-service]; an L7 proxy is simpler but adds latency to each call ✅[^ms-grpc-perf] | Requests per pod with k pods: each near 1/k of the total after the fix; connections per client = k with `round_robin`. The [Kubernetes Services doc](../../kubernetes/networking/services-and-kube-proxy.md) records a lab where one keep-alive connection hit 1 pod of 3 |

**Message size**

| Class | Signals in code | Fix | Before → after | Check |
|---|---|---|---|---|
| `unary-bulk-message` | A unary RPC whose response holds a whole file (`bytes data`), a full export or a `repeated` field with every row; a receive limit raised or removed to fit it: `MaxReceiveMessageSize = null`, grpc-go `MaxCallRecvMsgSize` or `MaxRecvMsgSize`, grpc-java `maxInboundMessageSize`, channel arg `grpc.max_receive_message_length = -1`; `RESOURCE_EXHAUSTED` errors "fixed" by a bigger limit | Server streaming in chunks (`returns (stream Chunk)`), or a paginated List method with a page token; large files outside gRPC (an HTTP stream or a presigned URL, see `app-proxied-transfer`) | Memory per call O(b) on both sides → O(chunk). gRPC is message-based: the entire message is in memory before it is sent and is deserialized whole on receipt ✅[^ms-grpc-perf]; for large binary payloads Microsoft advises avoiding them, considering splitting them with streaming, or considering not using gRPC for them, and notes a .NET byte array above 85,000 bytes lands on the large object heap ✅[^ms-grpc-perf]. Receive defaults: 4 MB for both server and client options in gRPC for .NET (ASP.NET Core 11.0 docs) ✅[^ms-grpc-config], 4MB for the client call option `MaxCallRecvMsgSize` and the server option `MaxRecvMsgSize` in grpc-go v1.85.0 ✅[^grpc-go], 4 MiB for `ManagedChannelBuilder.maxInboundMessageSize` (client side) in grpc-java 1.86.0 ✅[^grpc-java]. Send defaults differ: unlimited (`null`) in .NET ✅[^ms-grpc-config], `math.MaxInt32` in grpc-go (`MaxCallSendMsgSize` and `MaxSendMsgSize`) ✅[^grpc-go]; .NET warns that raising the receive limit can hurt memory consumption ✅[^ms-grpc-config] | Peak heap per call with b = 1 MB and b = 100 MB: grows with b before, flat after; a histogram of message sizes per method |

## Lookup notes

| Class | Not a problem when |
|---|---|
| `single-connection-stream-cap` | c stays well below s (a low-traffic client); the client already opens extra connections at the limit (.NET 5+ `GrpcChannel` with its own handler ✅[^ms-grpc-perf]); grpc.io says the gRPC team plans a feature to fix this queueing and calls any multiple-channel solution "a temporary workaround that should eventually not be needed" (page last modified 2024-11-12; it does not say whether the feature has shipped, so check the release notes of the version in use) ✅[^grpc-perf]. Raising the server limit instead is not recommended by Microsoft: more streams per connection add write contention and one lost packet blocks every call at the TCP layer ✅[^ms-grpc-perf] (see the [head-of-line blocking deep dive](../../web-apis/http2-http3-head-of-line-blocking-deep-dive.md)) |
| `rpc-connection-pinning` | k = 1; an L7 proxy or service mesh already balances per call; traffic is one long stream, which cannot be balanced once started anyway ✅[^grpc-perf]; many clients each pinned to a random backend can spread load evenly enough (an inference from connection-level balancing, not stated by a page) |
| `unary-bulk-message` | b has a small fixed bound (a single record, a thumbnail); the call is rare and the whole result is needed in memory anyway. grpc.io says streaming RPCs create extra threads, which makes them much slower than unary RPCs in gRPC Python, unlike the other languages (page states no version) ✅[^grpc-perf], so chunking there needs a measurement, or pagination with unary calls. Border with other catalogs: `oversized-message-payload` is a broker that stores and copies the message body, and `whole-object-transfer` is one `PUT` or `GET` to an object store; this class is a gRPC call whose message must be held whole in memory at both ends and hits the receive limit |

**Considered and not admitted as classes** (a reviewer may mention these as context, never as a finding):
- `small-flow-window`: a flow-control window too small for large messages over a high-latency link (signals: large uploads or client streaming to Kestrel with the default `InitialStreamWindowSize`; grpc-go `WithStaticStreamWindowSize` or `StaticStreamWindowSize` with a small value; `InitialConnectionWindowSize` smaller than `InitialStreamWindowSize`; fix: raise Kestrel's two window sizes, the connection window at least the stream window, or keep grpc-go dynamic flow control). It fails the admission test because the window default is not visible in the code under review, and the sources cover one server's uploads (Kestrel), not gRPC in general. Facts: Throughput per stream at most w / RTT (arithmetic: 768 KiB per 100 ms is about 7.5 MiB/s) → limited by bandwidth. Flow control can hurt performance when receiving large messages: with a window smaller than the payload, or latency between the peers, data moves in start/stop bursts ✅[^ms-grpc-perf]; Microsoft says to consider larger windows when a service often receives messages above 768 KB (Kestrel's default stream window), says the connection window should always be at least the stream window, and warns against an unnecessarily large window because it raises memory use ✅[^ms-grpc-perf]; Kestrel `InitialStreamWindowSize` is the request body data the server will buffer per stream, defaults to 768 KiB, range 64 KiB to under 2 GiB (ASP.NET Core 2.2 to 11.0), so it governs uploads to Kestrel, not responses it sends ✅[^kestrel-window]; in grpc-go v1.85.0, `WithStaticStreamWindowSize` and the server option `StaticStreamWindowSize` disable dynamic flow control, `WithStaticStreamWindowSize` also falls back to a static 64KB connection-level window, and for `WithInitialWindowSize` values below 64K are ignored ✅[^grpc-go]; the HTTP/2 initial window is 65,535 octets ✅[^rfc9113] Not a problem when: Messages are small (Microsoft suggests larger windows for services that often receive messages above 768 KB ✅[^ms-grpc-perf]); client and server are in one data centre with a low RTT; memory per connection is the tighter limit (a larger window lets Kestrel buffer more per stream ✅[^ms-grpc-perf]). grpc.io says flow control applies to streaming RPCs and is not relevant for unary RPCs ✅[^grpc-flow], while Microsoft describes start/stop bursts for large messages without making that split, so for unary calls the effect is unconfirmed
- `sync-call-chain`: a chain of synchronous calls between services (signals: a query handler that awaits another internal service, whose handler awaits a third, as in `orders` → `pricing` → `stock`; fix: replicate the few needed attributes through integration events, send follow-up actions asynchronously, return coarse-grained data). It fails the admission test because a diff shows one hop only and the fix is architectural. It is not a sub-case of `distributed-calls` (fan-out) or `concurrency-backpressure` (independent awaits in sequence), and d = 1 to a strict-latency service is covered by `distributed-calls` (a timeout and deadline propagation). Facts: Synchronous hops per read d → 0, so the added latency of about d × t per read and the product of d availabilities both drop out (arithmetic). Microsoft's .NET microservices guide (ms.date 2020-01-30) calls a chain of synchronous requests while serving a client request an anti-pattern, says the overall response time gets worse the more synchronous dependencies are added, and recommends replicating only the needed attributes into the initial service's database ✅[^ms-microservices]; it also says turning in-process calls directly into RPC calls causes chatty, inefficient communication ✅[^ms-microservices] Not a problem when: The call is a command that must succeed or fail now (payment authorisation), and the latency is part of the contract; the data changes too fast for a replica to be correct; d = 1 to a service with a strict latency budget (then apply `distributed-calls`: a timeout and deadline propagation)

**Belongs to an existing class** (not added here; the API-specific signal first):
- A GraphQL resolver that queries the database or calls a service once per parent object (`Book.author` resolved with one `SELECT` per book) → `io-batching-n-plus-one`, fixed with a per-request batch loader (DataLoader). graphql.org says the N+1 problem is commonly solved by collecting requests over a short period and dispatching them in a single request ✅[^graphql-perf].
- A REST or gRPC contract with only a per-item `Get`, so clients loop over ids; many unary calls in a loop → `io-batching-n-plus-one`, fixed with a batch method. AIP-231 makes `BatchGet` atomic (all succeed or all fail) and its example caps a batch at 1000 resources ✅[^aip-231]. Replacing unary calls with a bidirectional stream is faster in .NET once the stream is open, but Microsoft calls it an advanced technique not appropriate in many situations ✅[^ms-grpc-perf].
- A GraphQL schema with no depth, breadth, alias, batch or cost limit → `unbounded-input`. graphql.org recommends a maximum depth, a separate smaller limit for nested lists (nesting can grow the data exponentially), limits on aliases and on queries per batch, and query complexity analysis; it says the GraphQL specification gives no guidelines on complexity analysis or rate limits ✅[^graphql-security] (the latest release is the September 2026 edition ✅[^graphql-spec]). Server defaults differ: the Hot Chocolate docs at the `v15` URL (the page itself names no version) list `MaxFieldCost` 1,000, `MaxTypeCost` 10,000, `EnforceCostLimits` true and `SkipAnalyzer` false (so analysis runs unless bypassed), with cost-limit failures using error code `HC0047` ✅[^hc-cost].
- A GraphQL list field with no `first`/`after` arguments, or a REST or gRPC List method with no page size → `payload-overfetch` (and `unbounded-input` for the maximum). graphql.org says a List field that could return a lot of data should be paginated ✅[^graphql-security]; AIP-158 says an oversized `page_size` should be coerced down to the maximum ✅[^aip-158].
- Offset pagination (`?page=500&size=50`, `OFFSET`) written into a public contract → `db-query-index` (keyset pagination behind the API). AIP-158 requires opaque, URL-safe page tokens that users cannot parse ✅[^aip-158]; the Azure guidelines return an absolute `nextLink` for the next page ✅[^ms-azure-api]. An opaque token lets the server switch to keyset reads without a contract change (inference).
- An exact `total_size` or `count` computed on every page request → `sql-query-shape`. AIP-158 makes `total_size` optional and allows an estimate if documented ✅[^aip-158].
- A List method returning every field of every resource, or a client that must `PUT` the whole resource to change one field → `payload-overfetch`. AIP-157 says the effective default view for List should be `BASIC` ✅[^aip-157]; the Azure guidelines create and update with `PATCH` and a JSON Merge Patch body ✅[^ms-azure-api]; RFC 7240 defines `Prefer: return=minimal` for a minimal response ✅[^rfc7240]. Binary data sent as base64 in JSON adds 33% to the size, per Microsoft ✅[^ms-grpc-perf].
- Long work behind a synchronous request (a report, a bulk import) → `inline-slow-work`. AIP-151 says such a method should return a long-running operation and gives 10 seconds as a rule of thumb ✅[^aip-151]; the Azure guidelines return `202 Accepted` with an `operation-location` header and a `retry-after` header while not complete ✅[^ms-azure-api]; RFC 7240 lets a client ask for this with `Prefer: respond-async` ✅[^rfc7240]. A client that polls the operation in a tight loop and ignores `retry-after` → `polling-event-rate`.
- A gRPC channel or HTTP client created per call → `connection-management`. grpc.io says to re-use stubs and channels ✅[^grpc-perf]; Microsoft lists the socket, TCP, TLS (Transport Layer Security) and HTTP/2 set-up each new channel repeats ✅[^ms-grpc-perf].
- A gRPC call with no deadline, retries with no budget, or parallel calls to many services → `distributed-calls`.
- A GraphQL API reachable only by `POST`, so nothing is cached → `missing-cache-headers`. graphql.org says `GET` requests are typically considered cacheable by default and can help HTTP caching or a CDN (content delivery network) when caching headers are in the server response, within browser and CDN URL size limits; persisted queries let the client send a hash instead of the query ✅[^graphql-perf].
- GraphQL or JSON APIs served uncompressed → `response-compression`; graphql.org encourages gzip for production GraphQL services ✅[^graphql-perf].
- A server stream that writes without waiting for the reader → `concurrency-backpressure`.
- gRPC keepalive settings are a liveness concern, not a cost class here; see [../../grpc/stale-connection-keepalive.md](../../grpc/stale-connection-keepalive.md). The grpc.io table gives a client `KEEPALIVE_TIME` of INT_MAX (disabled) and a server one of 2 hours, with no per-language breakdown ✅[^grpc-keepalive]; the page says a server that does not support keepalive ignores the first few pings and then sends `GOAWAY` with `too_many_pings` ✅[^grpc-keepalive].

**Corrections found while checking the sources (2026-11-26):**
- "Add a `read_mask` field" is no longer Google's advice: AIP-157 marks a read mask as a single explicit request field DEPRECATED for Google APIs and says the system parameter must be used instead ✅[^aip-157].
- Streaming is not faster everywhere: grpc.io says streams cannot be load balanced once started, that they may help at small scale but can reduce scalability, and that they should only be used when they provide substantial performance or simplicity benefit; in gRPC Python streaming RPCs are much slower than unary ones ✅[^grpc-perf].
- Message limits are not symmetric: receive defaults are 4 MB in .NET and Go and 4 MiB for the grpc-java client builder, but send defaults are unlimited in .NET and `math.MaxInt32` in grpc-go ✅[^ms-grpc-config] ✅[^grpc-go].
- The Hot Chocolate v15 cost page contradicts itself on `DefaultListSize`: the text says 1, the options table says 50 ✅[^hc-cost]. Read the table for the version you run, or set the value.

**What the sources do not say:**
- The grpc.io performance page gives no default stream limit; the "100" comes from Microsoft ("most servers") and Kestrel ✅[^ms-grpc-perf] ✅[^kestrel-streams]. The grpc-go v1.85.0 sections read state no default for `MaxConcurrentStreams` ✅[^grpc-go].
- The grpc.io flow-control guide gives no default window sizes and mentions no BDP (bandwidth-delay product) estimation ✅[^grpc-flow].
- `MAX_CONNECTION_AGE`: the grpc.io keepalive page lists it as a server option, "Maximum time that a channel may exist", infinite by default, and states no load-balancing purpose, so this doc does not offer it as a fix for pinned connections ✅[^grpc-keepalive].
- grpc-js (Node.js) and gRPC C++ defaults were not read for this doc; check them before quoting a number for those implementations.

## Takeaways
- For every gRPC client, ask two questions: what balances calls across backends (`round_robin` over a headless Service, or an L7 proxy), and how many calls share one connection against the server's stream limit. [rule-candidate]
- A unary message whose size grows with data is a bug waiting for the 4 MB receive limit: stream it in chunks or paginate; do not raise the limit. [rule-candidate]
- Most API findings map to existing classes: name the existing class and give the API-specific fix (DataLoader, batch method, page token, LRO).
