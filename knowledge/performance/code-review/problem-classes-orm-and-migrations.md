# Performance problem classes in object-relational mappers and schema migrations

## Summary
**TL;DR:** An object-relational mapper (ORM) hides the SQL it sends, and a migration file hides the locks its statements take. This catalog names nine classes a reviewer can see in the code: a join that multiplies sibling collections, change tracking on read-only queries, a session that grows across a batch, SQL text that changes on every call, statements that grow with the input, and four migration shapes (a table rewrite, an index build that blocks writes, a constraint validated in one step, a backfill inside the migration). Each row gives the fix, the cost from the code, and the check.
**Use this when:** you review data-access code written with Entity Framework Core (EF Core), Hibernate, Django, SQLAlchemy, Mongoose or Prisma, or a migration that runs against a large PostgreSQL or MySQL table.
**Not this doc:** N+1 queries, missing indexes, query shape, over-fetching, lock scope and connection pools → `problem-classes.md` (`io-batching-n-plus-one`, `db-query-index`, `sql-query-shape`, `payload-overfetch`, `transaction-lock-scope`, `connection-management`); a LINQ or Django query enumerated twice → `lazy-reenumeration` in `problem-classes-language-runtimes.md`; a long batch job with no checkpoint → `unchunked-batch-job` in `problem-classes-messaging-and-jobs.md`; why PostgreSQL keeps dead rows → `../postgresql-mvcc-xid-wraparound-deep-dive.md`; `IQueryable<T>` and expression trees → `../../dotnet/collections-and-linq/linq.md`.

## Scope
The domain is the work an ORM or a migration tool generates on the database, which the application code does not show. Analogy: a travel agent books your trip. You say "two cities"; the agent may book every flight combination, keep a copy of every ticket, or close the airport while it repaints a gate. Concrete example: in EF Core, `ctx.Blogs.Include(b => b.Posts).Include(b => b.Contributors)` sends one query that returns posts × contributors rows per blog.

Covered: nine classes in three groups (loading and tracking, statement text and size, schema migrations). Not covered: database tuning settings, replication, and the shapes already in other catalogs (see "Belongs to an existing class" in Lookup notes).

Notation (each symbol is a count read from the code or its data):

| Symbol | Meaning | Worked example |
|---|---|---|
| n | Rows in the table or entities in the loop | An `orders` table of 50,000,000 rows: n = 50,000,000 |
| p₁, p₂ | Child rows per parent in two sibling collections | A blog with 10 posts and 10 contributors: p₁ = 10, p₂ = 10, so one joined query returns 10 × 10 = 100 rows, and split queries return 10 + 10 = 20 child rows |
| t | Entities tracked by one context or session | An import loop that adds 200,000 rows to one `DbContext`: t grows to 200,000 |
| k | Values in one `IN` list, or rows in one bulk insert | `ids.Contains(x.Id)` with 40,000 ids: k = 40,000 |
| c | Bound parameters per row of a bulk insert | Inserting rows of 5 columns: c = 5, so k = 10,000 rows need 50,000 parameters |
| b | Batch (chunk) size chosen by the code | Backfilling 1,000 rows per transaction: b = 1,000, so n = 50,000,000 rows take 50,000 transactions |

Terms:

| Term | Plain meaning | Analogy | Concrete example |
|---|---|---|---|
| Eager loading | Loading related rows in the same operation as the parent rows | Ordering the side dishes with the main course | EF Core `Include`, Django `prefetch_related`, SQLAlchemy `selectinload` |
| Split query | One SQL query per included collection instead of one big join | Separate receipts per shop instead of one receipt listing every pair | EF Core `AsSplitQuery()` |
| Change tracking | The ORM keeps a record of each loaded entity to detect edits later | A photocopy of each form so you can spot what was changed | EF Core snapshots; Hibernate dirty checking |
| Identity map / persistence context / first-level cache | The ORM's per-session table of loaded entities, one object per row | A cloakroom: one ticket per coat | Hibernate `Session`, EF Core change tracker, SQLAlchemy `Session` |
| Plan cache | Stored query plans reused for the same statement text | A recipe kept on file, found by its exact title | SQL Server's plan cache; PostgreSQL prepared statements (per session) |
| Bound parameter | A placeholder in SQL whose value is sent separately | A form with blanks, not a hand-written letter | `WHERE id = $1`, `@p0`, `?` |
| Table rewrite | The database copies every row into a new file | Reprinting the whole book to change one word on each page | PostgreSQL `ALTER COLUMN ... TYPE bigint` |
| Lock mode | How strongly a statement holds a table against other sessions | "Do not disturb" versus "closed for renovation" | PostgreSQL `ACCESS EXCLUSIVE`, `SHARE`, `SHARE UPDATE EXCLUSIVE` |
| `NOT VALID` constraint | A constraint enforced for new rows, with old rows checked later | A new rule for new members, with the old member list audited next week | `ADD CONSTRAINT fk ... NOT VALID`, then `VALIDATE CONSTRAINT fk` |
| Backfill | Filling a new column for existing rows | Writing the new phone extension into every old directory entry | `UPDATE users SET full_name = first || ' ' || last` |

## Catalog

**Loading and tracking**

| Class | Signals in code | Fix | Before → after | Check |
|---|---|---|---|---|
| `sibling-collection-join` | EF Core two `Include` calls on collections of the same parent (`.Include(b => b.Posts).Include(b => b.Contributors)`) with no `AsSplitQuery()` and no global splitting mode; EF Core's multiple-collections warning in the log; Hibernate HQL or an entity graph that `join fetch`es two collections; SQLAlchemy `joinedload` on two collections | EF Core `AsSplitQuery()` or `UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery)`; Hibernate subselect fetching for the second collection; SQLAlchemy `selectinload`; Django `prefetch_related` | Rows per parent p₁ × p₂ in 1 query → p₁ + p₂ in 1 + (number of collections) queries. On the current EF Core page (it names no version for this), sibling collections give a cross product, so 10 posts and 10 contributors return 100 rows for one blog ✅[^ef-split]; no explosion when the joins are not at the same level (`ThenInclude`) ✅[^ef-split]; a split query adds one SQL query and one round trip per included collection, gives no consistency guarantee across the queries, and on databases that allow only one active query at a time (SQL Server with MARS and SQLite are the page's exceptions) buffers earlier results in memory ✅[^ef-split]. Hibernate 7.4: joining both collections in one query gives a cartesian product of tables, and the guide suggests subselect fetching ✅[^hib-intro]. SQLAlchemy 2.1: `selectinload` is in most cases the simplest and most efficient way to eager-load collections ✅[^sqla-rel] | Rows returned by the statement against the sum of child rows (EF Core statement logging): Σ p₁·p₂ before, Σ (p₁ + p₂) after; EF Core logs a warning when a query loads multiple collections with no splitting mode set ✅[^ef-split] |
| `tracked-read-only-query` | EF Core queries whose results are only serialized or returned, with no `SaveChanges` in the scope and no `AsNoTracking()`; Hibernate queries in read-only service methods with no read-only setting; Mongoose `find()` results passed to `res.json` with no `.lean()` | EF Core `AsNoTracking()`, `UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking)`, or a `Select` projection to a non-entity type; `AsNoTrackingWithIdentityResolution()` when one row repeats in the result; Hibernate `setReadOnly(true)` on the query or `Session.setDefaultReadOnly(true)`; Mongoose `.lean()` | Per loaded entity one identity-map entry and one snapshot → none. EF Core keeps a dictionary of tracked instances and a snapshot of each one, which costs time and memory; no-tracking avoids both in read-only scenarios ✅[^ef-efficient]; the page's benchmark (10 blogs with 20 posts each) allocated 380.11 KB tracking against 232.89 KB no-tracking, mean 1,414.7 µs against 993.3 µs ✅[^ef-efficient]; a projection with no entity types is not tracked ✅[^ef-tracking]. Hibernate 7.4: an entity in read-only mode needs no dirty check ✅[^hib-intro]. Mongoose 9.13: `lean()` returns plain objects; the page's example document is about 180 bytes hydrated and about 55 bytes lean, a saving in process memory only ✅[^mongoose-lean] | EF Core `ChangeTracker.Entries().Count()` after the read: n before, 0 after; allocation profile of one request at two result sizes |
| `unbounded-unit-of-work` | One `DbContext`, Hibernate `Session` or SQLAlchemy `Session` held for a whole import or batch: `foreach (var row in rows) { ctx.Add(...); ctx.SaveChanges(); }` with `ctx` created outside the loop; `session.persist(e)` in a loop with no `clear()`; a context kept in a singleton or a long-running worker | A new short-lived context per chunk of b rows; EF Core `ChangeTracker.Clear()` after each chunk's `SaveChanges`; Hibernate `flush()` then `clear()` per chunk, or a `StatelessSession`; SQLAlchemy commit per chunk | Tracked memory O(n) → O(b); with `SaveChanges` per item on a growing context, each call scans every tracked entity, so Σ t = O(n²) entity checks → O(n·b) (arithmetic). EF Core 10 docs: a `DbContext` is designed as a short-lived unit of work, and `ChangeTracker.Clear` is more efficient than detaching entities one by one ✅[^ef-ct]; `SaveChanges` detects changes, and detection can become a performance problem for some applications that track thousands of entities (the page says the exact number depends on the entity, and that detection is not a bottleneck for most applications) ✅[^ef-detect]. Hibernate 7.4: the persistence context holds hard references to its entities, they are not evicted automatically, and `detach()` and `clear()` remove entities from the session cache ✅[^hib-intro]; a `StatelessSession` offers essentially everything except the first-level cache ✅[^hib-intro] | Tracked entities at the end of the loop (`ChangeTracker.Entries().Count()`): n before, at most b after; heap and time per chunk at n and 2n: flat after the fix |

**Statement text and size**

| Class | Signals in code | Fix | Before → after | Check |
|---|---|---|---|---|
| `statement-text-churn` | SQL built by concatenation or interpolation of values (`"... WHERE id = " + id`, `FromSqlRaw("..." + name)`, a Python f-string passed to `execute`); EF Core dynamic predicates built with `Expression.Constant(value)`; `EF.Constant(list)` or EF Core before 8.0 inlining `ids.Contains(x.Id)` as `IN (1, 2, 3)`; an IN list rendered with `string.Join` | Bound parameters (`FromSql` with an interpolated `FormattableString`, driver placeholders); in EF Core, a captured variable instead of `Expression.Constant`; for lists, one array parameter (`id = ANY($1)` in PostgreSQL) or EF Core 10's padded parameter lists; prepared statements in the driver | One ORM compile per distinct value, and on a database with a shared plan cache one plan per distinct SQL text → one of each per statement shape. EF Core: queries that differ by a constant are compiled separately and produce different SQL, so the database server will likely also need a plan for each ✅[^ef-adv] (the page names SQL Server as keeping an implicit plan cache and PostgreSQL as not keeping one ✅[^ef-adv]); `Expression.Constant` recompiles the query on each new value and usually pollutes the database plan cache ✅[^ef-adv]; before EF Core 8.0 inlined lists gave different SQL per list, causing plan-cache misses and bloat; EF Core 10 sends one parameter per value and pads the list (8 values → 10 parameters) ✅[^ef10]. PostgreSQL 19: `PREPARE` avoids repeated parse analysis, helps most when one session runs many similar statements, and lasts only for the session ✅[^pg-prepare]; `IN (...)` is shorthand for a chain of `OR`s, while `ANY` takes one array value ✅[^pg-any] | EF Core's Query Cache Hit Rate metric reaches 100% soon after startup in a normal application; a value stuck below 100% points to a defeated cache ✅[^ef-adv]; PostgreSQL `pg_stat_statements` with `track_planning` on (default off, and `plans` is zero while it is off): `plans` counts planning runs and `calls` executions, and the page says a cached plan makes them differ ✅[^pg-pgss]; so `plans` close to `calls` for a hot statement shows it is planned on almost every call (inference; it does not by itself tell churn from missing prepared statements) |
| `unbounded-statement-size` | `Where(x => ids.Contains(x.Id))`, `filter(id__in=ids)`, `In(ids)` where `ids` comes from an earlier query, a file or a job argument of unknown size; Django `bulk_create(objs)` or `bulk_update(objs, fields)` with no `batch_size` on large lists; one multi-row `INSERT ... VALUES` built for all rows | Fixed chunks of b (`batch_size=b`, or a loop over slices); one array parameter (`= ANY($1)`) in PostgreSQL; a join against a temporary table; `COPY` for bulk loads (→ `io-batching-n-plus-one`) | Parameters per statement k·c → b·c; statement text O(k) → O(b); a hard failure when k·c passes the engine limit → none. SQLite: the maximum host parameter number defaults to 32,766 since 3.32.0 and 999 before ✅[^sqlite-limits]. SQL Server 2016 and later: the capacity page lists 2,100 parameters per stored procedure and per user-defined function, and a batch of 65,536 × the network packet size (4 KB by default) ✅[^mssql-cap]. PostgreSQL 19: the Bind message carries the number of parameter values as an Int16 ✅[^pg-proto], a 16-bit field, so a count that 16 bits cannot hold cannot fit (inference; the page states no maximum). Django 6.1: `bulk_create` by default puts as many objects in one batch as the database allows, SQLite and Oracle limit parameters, `bulk_update` can generate very large SQL, and the docs advise a suitable `batch_size` ✅[^dj-qs]; some databases limit the terms in an `IN` clause ✅[^dj-qs] | Largest k in production (row count of the source); a test with k above the limit (for example 40,000 ids on SQLite, above 32,766): fails before, passes after with ⌈k / b⌉ statements (arithmetic) |

**Schema migrations**

| Class | Signals in code | Fix | Before → after | Check |
|---|---|---|---|---|
| `table-rewriting-ddl` | PostgreSQL migration with `ADD COLUMN ... DEFAULT clock_timestamp()` (or another volatile function), a stored generated column, an identity column, or a constrained domain type; `ALTER COLUMN ... TYPE` (EF Core `AlterColumn` with a new type, Django `AlterField` changing the field class); MySQL `MODIFY COLUMN` with a new data type; MySQL `ADD COLUMN` on a `ROW_FORMAT=COMPRESSED` or `FULLTEXT` table; no `lock_timeout` in the migration | PostgreSQL: add the column with no default or a non-volatile default, then fill it in batches (`in-migration-backfill`); change a type by adding a new column, backfilling and switching reads; set `lock_timeout` so a blocked migration fails fast. MySQL 8.4: write `ALGORITHM=INSTANT` (or `INPLACE, LOCK=NONE`) explicitly, so the statement fails instead of choosing a table copy | A rewrite of all n rows and every index under the strongest lock → a metadata-only change. PostgreSQL 19: `ALTER TABLE` takes `ACCESS EXCLUSIVE` unless noted ✅[^pg-alter], the only mode that blocks a plain `SELECT` ✅[^pg-locks]; a non-volatile default is stored in metadata with no rewrite, while a volatile default, a stored generated column, an identity column or a constrained domain rewrites the table and its indexes ✅[^pg-alter]; a type change normally rewrites both, except when `USING` keeps the value and the old type is binary coercible to the new one, and even then indexes may be rebuilt ✅[^pg-alter]; rebuilds can take a long time on a large table and need up to double the disk space ✅[^pg-alter]; `lock_timeout` aborts a statement that waits too long for a lock and is 0 (off) by default ✅[^pg-client]. MySQL 8.4: `INSTANT` is the default algorithm in MySQL 8.4, and adding a column has limits (not on `ROW_FORMAT=COMPRESSED` tables, tables with a `FULLTEXT` index, or temporary tables; at most 64 row versions, 255 as of MySQL 9.1.0), and the table is rebuilt if `ALGORITHM=INPLACE` is used to add a column ✅[^mysql-ops]; a type change is supported only with `ALGORITHM=COPY`, which permits no concurrent DML ✅[^mysql-ops]; naming an `ALGORITHM` requires that algorithm for the clauses and engines that support it and otherwise fails with an error, while omitting it uses `INSTANT` where supported, then `INPLACE`, then `COPY` ✅[^mysql-alter] | On a restored copy, run the migration while a second session reads `pg_locks` for the table (`mode`, `granted`) ✅[^pg-pglocks]: `AccessExclusiveLock` granted for the whole run before, only briefly after; MySQL: the explicit `ALGORITHM=INSTANT` statement succeeds |
| `write-blocking-index-build` | PostgreSQL `CREATE INDEX` without `CONCURRENTLY` on a large, written table: Django `AddIndex` or a new `Meta.indexes` entry, EF Core `migrationBuilder.CreateIndex`, a raw `CREATE INDEX` in a migration that runs in a transaction | PostgreSQL `CREATE INDEX CONCURRENTLY` outside a transaction: Django `AddIndexConcurrently` in a migration with `atomic = False`; EF Core `migrationBuilder.Sql("CREATE INDEX CONCURRENTLY ...", suppressTransaction: true)`; for a partitioned table, build each partition's index concurrently, then the parent index. MySQL 8.4: `ALGORITHM=INPLACE, LOCK=NONE` | Writes blocked for one full build → writes continue, at the price of two table scans and waits for older transactions. PostgreSQL 19: a normal build blocks inserts, updates and deletes until it finishes ✅[^pg-cidx]; it takes a `SHARE` lock, which conflicts with the `ROW EXCLUSIVE` lock that `UPDATE`, `DELETE`, `INSERT` and `MERGE` take ✅[^pg-locks]; `CONCURRENTLY` takes no lock that blocks writes, scans the table twice, waits for transactions that could use the index, cannot run in a transaction block, and on failure leaves an invalid index that still costs update overhead (drop it and retry) ✅[^pg-cidx]; concurrent builds on partitioned tables are not supported, and only one concurrent build runs per table at a time ✅[^pg-cidx]. Django 6.1 notes that `CONCURRENTLY` is not supported inside a transaction ✅[^dj-pgops]; EF Core in most cases wraps each migration in its own transaction, and `suppressTransaction: true` on `migrationBuilder.Sql` opts out for operations a database cannot run in a transaction ✅[^ef-migr]. MySQL 8.4: a secondary index is built in place and the table stays available for reads and writes ✅[^mysql-ops]; `LOCK=NONE` permits concurrent queries and DML, and a `LOCK` clause less restrictive than the operation permits makes the statement fail ✅[^mysql-perf] | During the build, `pg_stat_progress_create_index` shows the phase `waiting for writers before build` only in concurrent mode ✅[^pg-progress]; inserts from a second session complete during the build after the fix and wait before it |
| `one-step-constraint-validation` | PostgreSQL `ADD CONSTRAINT ... FOREIGN KEY` or `CHECK` with no `NOT VALID` on a large table; `ALTER COLUMN ... SET NOT NULL` (EF Core `AlterColumn(nullable: false)`, Django `AlterField` dropping `null=True`); Django `AddConstraint` on a large PostgreSQL table; MySQL `ADD FOREIGN KEY` with `foreign_key_checks` on | PostgreSQL: `ADD CONSTRAINT ... NOT VALID` in one migration, `VALIDATE CONSTRAINT` in a later one (Django `AddConstraintNotValid` then `ValidateConstraint` for a check constraint, in two migrations); for `NOT NULL`, a not-null constraint added `NOT VALID` then `VALIDATE CONSTRAINT`, or a validated `CHECK (col IS NOT NULL)` first so that `SET NOT NULL` skips the scan | A scan of all n rows while holding a lock that blocks writes → an add that skips the scan of existing rows and can be committed immediately ✅[^pg-alter], then the scan under a lock that lets writes continue. PostgreSQL 19: `NOT VALID` is allowed for foreign-key, `CHECK` and not-null constraints ✅[^pg-alter]; `ADD FOREIGN KEY` takes `SHARE ROW EXCLUSIVE` on both the table and the referenced table ✅[^pg-alter], a mode that protects a table against concurrent data changes ✅[^pg-locks]; most other `ADD` constraint forms take `ACCESS EXCLUSIVE` ✅[^pg-alter]; `VALIDATE CONSTRAINT` takes only `SHARE UPDATE EXCLUSIVE` (plus `ROW SHARE` on a referenced table) ✅[^pg-alter], which does not conflict with `ROW EXCLUSIVE` ✅[^pg-locks]; `SET NOT NULL` scans the whole table unless `NOT VALID` is given or a valid `CHECK` proves no `NULL` exists ✅[^pg-alter]. Django 6.1 says `AddConstraintNotValid` and `ValidateConstraint` (both for check constraints) belong in two separate migrations, because in one atomic migration they act like `AddConstraint` ✅[^dj-pgops]. MySQL 8.4: adding a foreign key supports `INPLACE` only with `foreign_key_checks` disabled, otherwise only `COPY` ✅[^mysql-ops] | `pg_locks` during a staging run: no `ShareRowExclusiveLock` or `AccessExclusiveLock` held through a long scan after the fix ✅[^pg-pglocks]; writes from a second session complete while `VALIDATE` runs |
| `in-migration-backfill` | `migrationBuilder.Sql("UPDATE big_table SET ...")` in the same migration as the `AddColumn`; Django `RunPython` looping over `Model.objects.all()` with `save()` in an atomic migration; one `UPDATE t SET new_col = f(old_col)` over all rows next to schema changes | Separate the backfill from the schema change; run it in batches of b rows, each in its own transaction (Django: `atomic = False` with `transaction.atomic()` per batch, as in the Django docs' 1,000-row example); add constraints after the backfill (`one-step-constraint-validation`) | One transaction that holds n row locks, n dead row versions and the migration's table locks until commit → b rows per transaction. Django 6.1 runs all operations of a migration in one transaction on PostgreSQL and SQLite, and suggests `atomic = False` for data migrations on large tables ✅[^dj-migr] ✅[^dj-writing]; EF Core in most cases wraps each migration in its own transaction, and EF Core 9 spanned all pending migrations with one, reverted in EF Core 10 ✅[^ef-migr]. PostgreSQL 19: a lock is normally held until the end of the transaction ✅[^pg-locks]; an `UPDATE` leaves the old row version until `VACUUM` reclaims it, and plain `VACUUM` may not be enough after massive update activity ✅[^pg-vacuum]. MySQL: no transactions around schema changes, and where locks are needed their duration grows with the rows involved (Django 6.1's MySQL notes, written about the improvements since MySQL 8.0) ✅[^dj-migr] | Longest transaction during the migration on a staging copy: O(n) before, O(b) after |

## Lookup notes
- **Sizes decide.** Every class here scales with rows. A lookup table of 200 rows, a test database, or a migration on a table created in the same release is not a finding. Report these classes on tables or loops whose size comes from production data.
- **Not a problem when.**

| Class | Not a problem when |
|---|---|
| `sibling-collection-join` | The included collections are on different levels (`Include(...).ThenInclude(...)`) ✅[^ef-split]; the collections are small and bounded (one or two rows each); the result must be one consistent snapshot and the extra rows are cheap, since split queries give no consistency guarantee ✅[^ef-split]; the database is far away and round trips cost more than duplicate rows ✅[^ef-split] |
| `tracked-read-only-query` | The entities are changed and saved in the same unit of work; the same row appears many times in the result, where a tracking query returns one shared instance and a no-tracking query duplicates it ✅[^ef-efficient] (or use `AsNoTrackingWithIdentityResolution`); the query already projects to a non-entity type ✅[^ef-tracking]; the Mongoose route modifies the documents or calls `save()`, or relies on getters, setters, virtuals or casting, which lean documents lack ✅[^mongoose-lean] |
| `unbounded-unit-of-work` | The loop is short and bounded; the tracked entity count is small, since EF Core change detection is not a bottleneck for most applications ✅[^ef-detect]; the context is created per request and disposed at its end, the normal EF Core lifetime ✅[^ef-ct]; SQLAlchemy 2.1 objects that are not pending, deleted or modified are only weakly referenced by the session, so a read-only loop does not pin them ✅[^sqla-state] |
| `statement-text-churn` | The constant set is small and fixed (a status enum), where EF Core says constants are fine and sometimes allow optimizations parameters do not ✅[^ef-adv]; on PostgreSQL with no prepared statements (a driver may prepare for you): it keeps no implicit plan cache ✅[^ef-adv], so a bound parameter then saves the ORM's compile; whether it saves a database plan depends on prepared statements (inference); the statement runs rarely (an admin report). SQL injection is a separate, stronger reason to parameterize, and EF Core 10 adds an analyzer that warns on concatenation in raw SQL calls ✅[^ef10] |
| `unbounded-statement-size` | k is bounded by the code (a page of 50 ids, a fixed list of regions); the input is already capped by the caller (→ `unbounded-input`) |
| `table-rewriting-ddl` | The table is small or new; the change is metadata-only on this engine version (a non-volatile default in PostgreSQL 19, an `INSTANT` column add in MySQL 8.4) ✅[^pg-alter] ✅[^mysql-ops]; a maintenance window allows the table to be blocked for the rewrite |
| `write-blocking-index-build` | The table is new or empty, or not written during the build; the index is created in the same migration that creates the table; the database is MySQL 8.4, where the in-place build already allows reads and writes ✅[^mysql-ops] |
| `one-step-constraint-validation` | The table is small; the constraint is created together with the table; a valid `CHECK` already proves the column has no `NULL`, so `SET NOT NULL` skips the scan ✅[^pg-alter] |
| `in-migration-backfill` | The table is small; the column can be computed on read or given a non-volatile default instead ✅[^pg-alter]; the backfill touches only a few rows selected by an index |

- **Belongs to an existing class.**
  - Lazy loading inside a loop (`blog.Posts` read per blog, EF Core lazy-loading proxies, SQLAlchemy default `lazy="select"`) → `io-batching-n-plus-one`; EF Core recommends against lazy loading because it makes the N+1 problem easy to trigger ✅[^ef-efficient], and SQLAlchemy 2.1's `raiseload` turns a lazy load into an error ✅[^sqla-rel].
  - Whole entities loaded for one column (`ctx.Blogs` then `blog.Url`), and an `ORDER BY` with `Skip`/`Take` → `payload-overfetch` and `db-query-index`; EF Core shows both ✅[^ef-efficient].
  - Load, modify and `SaveChanges` for every row of a set (instead of `ExecuteUpdate`, Django `queryset.update()`) → `sql-query-shape` (one set-based statement) or `io-batching-n-plus-one` (per-item writes).
  - `ToList()` on a large result where a stream fits (EF Core `AsAsyncEnumerable`, Django `iterator()`) → `payload-overfetch`. EF Core also buffers internally under a retrying execution strategy and for all but the last split query ✅[^ef-efficient].
  - A `DbContext` created per request with no pooling, and a connection per call → `connection-management`; EF Core's `AddDbContextPool` reuses context instances ✅[^ef-adv].
  - An index added by a migration but never queried → `excess-write-indexes` in `problem-classes-datastores.md`.
  - A backfill or purge that runs as a background job with no checkpoint → `unchunked-batch-job` in `problem-classes-messaging-and-jobs.md`. `in-migration-backfill` is the case where the whole update sits inside the schema migration's own transaction, next to its table locks.
  - A transaction left open after `BEGIN`, and row locks held across remote calls → `transaction-lock-scope`.
  - `sibling-collection-join` is the ORM-generated form of `join-row-explosion` (in `problem-classes-data-pipelines.md`); it gets its own row because the signal is a loader option, not a join key, and the fix is a loading strategy.
- **Corrections found while checking the sources (2026-11-26).**
  - "Parameterize so the database reuses the plan" holds as stated for SQL Server, which keeps an implicit plan cache; PostgreSQL keeps none, so the reuse comes from prepared statements ✅[^ef-adv]; the page names only these two engines, so a claim about another engine (Oracle, MySQL) needs that engine's own page. A prepared statement lasts for one session, and by default its first five executions use custom plans before a generic plan is compared with their average cost ✅[^pg-prepare].
  - PostgreSQL 19 `pg_stat_statements` merges statements that differ only in constants and squashes IN lists of different lengths into one entry ✅[^pg-pgss], so its entry count hides `statement-text-churn`; compare `plans` with `calls` instead.
  - EF Core before 8.0 inlined `Contains` lists as constants; EF Core 8 sent one JSON array parameter, which hid the list length from the planner; EF Core 10 sends padded scalar parameters by default and lets the mode be changed with `UseParameterizedCollectionMode` ✅[^ef10]. Advice about `Contains` therefore depends on the EF Core version.
  - A SQLAlchemy 2.1 session does not pin every loaded object: objects are weakly referenced, except pending, deleted or modified ones, and after a full flush all are weak again ✅[^sqla-state]. A Hibernate 7.4 persistence context, in contrast, holds hard references ✅[^hib-intro].
  - Adding a column with a non-volatile default is not a rewrite in PostgreSQL 19 (the value lives in metadata) ✅[^pg-alter]; the page does not say since which version, and the advice "never add a column with a default" applies only to volatile defaults and the other listed forms.
  - `CREATE INDEX CONCURRENTLY` is not free: two scans, waits for older transactions, and an invalid index left behind on failure that still slows writes ✅[^pg-cidx].
  - In MySQL 8.4, a pending exclusive metadata lock requested by an online DDL statement blocks later transactions on the table ✅[^mysql-perf], so even an "online" change can stall traffic behind one long transaction.
- **What the sources do not say.**
  - No PostgreSQL 19 page read today states the exact maximum number of bind parameters; the protocol page gives only the Int16 field type ✅[^pg-proto]. Figures such as 32,767 or 65,535 are not from these pages.
  - The SQL Server capacity page lists 2,100 parameters per stored procedure and per function ✅[^mssql-cap]; it does not say how that limit applies to a parameterized statement sent by a driver.
  - No PostgreSQL 19 page read today states that a waiting `ACCESS EXCLUSIVE` request blocks later readers; only MySQL 8.4 states the metadata-lock form of this ✅[^mysql-perf]. `lock_timeout` is cited only for what it does ✅[^pg-client].
  - The EF Core benchmark numbers come from one machine and one shape (10 blogs with 20 posts) ✅[^ef-efficient]; the page gives no general ratio. The Mongoose sizes are the page's example ✅[^mongoose-lean].
  - Prisma ORM v7's `relationLoadStrategy` (Preview) defaults to `join`, a `LATERAL JOIN` with JSON aggregation on PostgreSQL, and `query` sends one query per table ✅[^prisma-rel]; the page does not say whether `join` multiplies sibling collections, so Prisma is not listed in `sibling-collection-join`.
  - The PostgreSQL page does not state which lock `SET NOT NULL` takes when it validates a not-null constraint added `NOT VALID`, so the fix above uses `VALIDATE CONSTRAINT`, whose lock the page gives ✅[^pg-alter]. No page read today says what EF Core 10 does when a `Contains` list has more values than the database's parameter limit.
  - The Hibernate 7.4 user guide's batch-insert chapter could not be read in full today; the claims above come from the Hibernate 7.4 short guide only, and the `flush()` then `clear()` fix is the usual pattern, not a quoted one.

**Calibration state (2026-11-26).** None of these classes has a sample in the review-agent calibration yet: see [perf-reviewer-calibration.md](perf-reviewer-calibration.md).

## Takeaways
- Read the SQL the ORM sends: two sibling `Include`s, tracking on a read-only path and one context for a whole batch each multiply work by a count you can read from the code. [rule-candidate]
- A value inside SQL text, or a list whose length comes from data, makes a new statement per call and has no upper bound; bind values and chunk lists. [rule-candidate]
- In a migration on a large table, name the lock each statement takes and whether it rewrites or scans: prefer metadata-only adds, `CONCURRENTLY`, `NOT VALID` then `VALIDATE`, and a batched backfill outside the migration transaction. [rule-candidate]
