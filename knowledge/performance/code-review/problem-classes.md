# Performance problem classes for code review

## Summary
**TL;DR:** Many slow code paths fit a set of named classes: a code shape with a known better structure, a known before → after cost, and a known way to confirm it. A reviewer who names the class can propose the fix and its cost from the code alone, before anything is slow. The speedup in time still needs a measurement.
**Use this when:** you review code for performance, or build a reviewer (person, lint rule or agent) that does; you need the fix and the cost for a code shape you have spotted.
**Not this doc:** how each structure works → `../../algorithms/`; database tuning in depth → `../database-query-performance.md`; how to run a fair benchmark → `../measurement/benchmarking-methodology.md`; the agent built on this catalog and its calibration → `perf-reviewer-calibration.md`.

## Scope
A **problem class** is a code shape that costs more than it needs to as input grows, together with its standard remedy. Analogy: a doctor's differential diagnosis. Symptoms (the shape) point to a named condition (the class), which has a standard treatment (the fix) and a test that confirms it (the check). One concrete row: `orders.map(o => customers.find(c => c.id === o.customerId))` is class `lookup-in-loop`; a `Map` built once turns O(n·m) into O(n + m); a scaling test shows the growth exponent fall from about 2 to about 1.

Notation: O(f(n)) says how work grows with the input size n, not how many seconds it takes ([complexity foundation](../../algorithms/fundamentals/complexity-and-big-o.md)). n, m and k are sizes taken from the code or its workload, V and E are a graph's vertices and edges, and Q is a number of queries.

Covered: 39 classes, in five groups: in-memory algorithms, memory, data access, concurrency with distributed calls and rendering, and three classes that apply only with a measured need. Not covered: compiler-level tuning, SIMD, GPU work.

## Lookup notes
- **Sizes decide.** A nested loop over sizes the code or workload fixes small (weekdays, a few config entries) is not a finding. A search inside each element's own sub-collection costs the total size, not n·m.
- **When the usual advice does not apply.**
  - A full sort is right when the whole sorted list is used.
  - A sequential scan is right on a small table.
  - Awaiting in a loop is right when iterations depend on each other ✅[^eslint-await].
  - With React Compiler, components and hooks are memoized automatically; react.dev advises relying on it for new code and keeping existing manual memoization ✅[^react-compiler].
- **Corrections found while checking the sources (2026-11-25).**
  - Boost states Dijkstra as O(V log V + E) and names no heap; the familiar O((V + E) log V) for a binary heap rests here on Wikipedia ✅[^wiki-dijkstra] and on a textbook's E log V ✅[^algs4-sp].
  - Python's `heapq` page gives no O(log n) for push or pop; it calls removing the root "clearly logarithmic" in its theory section ✅[^py-heapq].
  - PostgreSQL 19 includes buffer counts by default when `ANALYZE` is used ✅[^pg-explain]; PostgreSQL 19 can skip-scan a multicolumn index when the leading column has few distinct values and a later column has a condition, so the leading-column rule is no longer absolute ✅[^pg-multicol].
  - MDN does not say `Promise.all` limits concurrency; it says promises represent work already in progress ✅[^mdn-promise].
- **More corrections, from the classes added later on 2026-11-25.**
  - MDN calls throttling a scroll handler with `requestAnimationFrame` useless, because both fire at about the same rate; throttle by time or use `IntersectionObserver` ✅[^mdn-scroll].
  - Django 6.0's Tasks framework only enqueues work, apart from its development-only Immediate backend: production needs a separate worker to run it ✅[^django-tasks].
  - No rank 1 page was found for "do no I/O while holding a lock"; the statement in this catalog rests on the C# rule to hold locks briefly.
- **What the sources do not say.** Python's cost table has no row for `list.count`, `sum` or `str.join`; C's `strlen` page states no cost; AIP-158 says a server "should coerce" an oversized page size to its maximum, not that it must reject it.
- **Calibration state.** Every class except `data-layout-locality` has at least one known-bad sample in the review-agent calibration (`perf-reviewer-calibration.md` §6 and §6.3); 18 known-good samples test the "when the usual advice does not apply" cases.
- **Weaker sources, rank 5 or 6.**
  - Held–Karp solves the travelling salesman problem in Θ(n²·2ⁿ) against Θ(n!) for brute force ✅[^wiki-heldkarp]; greedy set cover is within about ln n of the optimum ✅[^wiki-setcover]. The original papers could not be read.
  - Aho–Corasick matching is linear in the text plus the number of matches once the automaton is built, and building is linear in the total keyword length ✅[^wiki-ac].
  - A centered interval tree answers a query in O(log n + m), with m the reported intervals ✅[^wiki-interval].
  - Bloom filters give false positives, never false negatives ✅[^wiki-bloom].
  - The hedged-request numbers of "The Tail at Scale" were read only in a summary; the paper's full text could not be read.
- **Latency orders of magnitude.** Main memory about 100 ns, reading 1 MB sequentially from disk about 20 ms, a packet from the US to Europe and back about 150 ms ✅[^norvig]. These are numbers from an undated table on a page written between 2001 and 2014: use them to compare kinds of operations, not as timings.
- **Classification source.** Skiena's catalog groups problems as data structures, numerical, combinatorial, graph (polynomial and hard), computational geometry, and set and string problems ✅[^skiena]. The classes above follow what code review meets, so several of them (N+1, retries, rendering) have no counterpart in that algorithms catalog.

## Takeaways
- Name the class, then derive the before → after cost from the code with sizes from the workload; never state a time speedup as fact without a measurement. [rule-candidate]
- Check every finding against the sizes note and "When the usual advice does not apply" in Lookup notes before reporting it. [rule-candidate]
- Confirm a growth-class claim with a scaling test, a round-trip claim with a query count, and an index claim with a plan.
