# Bun built-in utilities: a catalog for 1.4.5

## Summary
**TL;DR:** Bun ships, on the `Bun` global and as globals, the helpers that Node.js projects usually install from npm: hashing and password hashing, globbing, semver, parsers for TOML, YAML, JSON5, JSONC, JSONL, XML and Markdown, an HTML (HyperText Markup Language) rewriter, a TypeScript transpiler, compression, tar archives, CSRF tokens, cron, image processing, colours, S3 and Redis clients, and a headless browser (`Bun.WebView`). This catalog gives each one's call, its default, and what it returned in Bun 1.4.5, against real Redis, S3 and browser processes where the API needs one.
**Use this when:** looking up whether Bun has a built-in for a task, its exact name and default, or what it returns, before adding an npm dependency.
**Not this doc:** files and `Bun.write` → [file-io.md](file-io.md); `Bun.spawn` and `$` → [processes-and-shell.md](processes-and-shell.md); `Bun.sql` → [sqlite-and-sql.md](sqlite-and-sql.md); `fetch`, sockets and cookies → `bun/http-and-networking/networking-apis-reference.md`.

## Scope
Bun 1.4.5 (`1.4.5+a7733435c`) on Linux arm64, in the `oven/bun:1.4.5` image unless a row names another. Every "Lab" cell ran on 2026-11-24 with the input shown. The S3 rows ran against versitygw v1.11.0, an S3-compatible gateway (a server that answers the Amazon S3 HTTP API), and the Redis rows against Redis 7.4.12 (`redis:7-alpine`), both on a private Docker network; the OS-level cron and Linux WebView rows ran in `bunlab:2`, which adds cron and Chromium 156; the macOS WebView and `Bun.Image` rows ran a binary cross-compiled with `--target=bun-darwin-arm64` on an Apple-silicon Mac (macOS 26.1, Apple M2). Where something could not run here, its row says why. A built-in is like a tool that comes in the toolbox you already bought: no install step, but you still need to know which drawer it is in. Example: `Bun.semver.satisfies("1.4.5", "^1.4.0")` → `true` with no `semver` package installed.

### Hashing and passwords
| API | What it does | Lab (1.4.5) | Default / notes |
|---|---|---|---|
| `Bun.hash(input, seed?)` | Fast non-cryptographic 64-bit hash (a fingerprint for hash tables and caches, not for security) ✅[^1] | `Bun.hash("some data here")` → `11562320457524636935n`; seed `1234` → `15724820720172937558n` ✅[^lab] | Wyhash; input string, typed array, `DataView`, `ArrayBuffer` ✅[^1]: `Bun.hash(s)` equalled `Bun.hash.wyhash(s)`, and the same bytes as a string, `Uint8Array`, `DataView` and `ArrayBuffer` gave one value ✅[^lab] |
| `Bun.hash.wyhash/crc32/adler32/cityHash32/cityHash64/xxHash32/xxHash64/xxHash3/murmur32v3/murmur32v2/murmur64v2/rapidhash` | Other non-cryptographic hashes ✅[^1] | `crc32("data")` → `2918445923`; `xxHash3("data")` → `16480804363271232798n` ✅[^lab] | 32-bit ones return `number`, 64-bit ones `bigint` ✅[^1] ✅[^lab] |
| `new Bun.CryptoHasher(alg, hmacKey?)` | Incremental cryptographic hash or HMAC (hash-based message authentication code, a keyed hash) ✅[^1] | `sha256` of `hello` → `2cf24dba…9824`; with key `"key"` → `9307b3b9…8b7b` ✅[^lab] | 19 algorithms, `blake2b256` … `sha3-512`, `shake128`, `shake256` (`CryptoHasher.algorithms`) ✅[^lab] |
| `Bun.SHA256.hash(input, "hex")`, `Bun.SHA1`, `Bun.MD5` … | One-shot hash classes ✅[^22] | Same digest as `CryptoHasher` ✅[^lab] | — |
| `Bun.sha(input, "hex")` | One-shot SHA-512/256 ✅[^22] | Equals `CryptoHasher("sha512-256")` ✅[^lab] | — |
| `Bun.password.hash(pw, opts?)` / `.verify(pw, hash)` | Slow, salted password hashing ✅[^1] | Default → `$argon2id$v=19$m=65536,t=2,p=1$…`; `{ algorithm: "bcrypt" }` → `$2b$10$…`; verify → `true`, wrong password → `false` ✅[^lab] | Default argon2id, memory 65,536 KiB, 2 iterations ✅[^1] ✅[^lab]; bcrypt cost 10 ✅[^22]; bcrypt input over 72 bytes is pre-hashed with SHA-512 ✅[^1], so a 100-byte password verified and its 72-byte prefix did not ✅[^lab]; `hashSync`/`verifySync` block the thread ✅[^1]: a 1 ms interval fired 0 times during a 133 ms `hashSync` and 34 times during a 99 ms `await hash()` ✅[^lab] |

| API | What it does | Lab (1.4.5) | Default / notes |
|---|---|---|---|
| `Bun.s3` / `new Bun.S3Client(opts)` | S3-compatible object storage client ✅[^19] | `presign("x.txt", { expiresIn: 60 })` with test credentials built a signed URL with no server (`X-Amz-Algorithm=AWS4-HMAC-SHA256…X-Amz-Expires=60`) ✅[^lab]. ## Lookup notes
- **Present in 1.4.5 although some docs pages omit them:** `Bun.YAML.stringify`, `Bun.JSONC.parse`, `Bun.markdown.ansi`, `Bun.deepMatch`, `Bun.randomUUIDv5`, `Bun.sha` (all `typeof` `function`/`object` in the lab, documented in the type definitions) ✅[^lab] ✅[^22]. **Absent:** `Bun.Markdown` (use `Bun.markdown`), `Bun.HTMLRewriter` (use the global `HTMLRewriter`), `Bun.JSONL.stringify` ✅[^lab]. Nothing listed in the 1.4.5 docs for this catalog was missing.
- `Bun.hash` results are stable for the same input and seed but are not cryptographic: use `CryptoHasher` or `Bun.password` for anything an attacker controls ✅[^1].
- A `RedisClient` with no server keeps retrying before it rejects (31.2 s, median of 5 runs, which is the sum of the reconnect schedule); set `maxRetries` or `connectionTimeout`, or check `connected` in health checks ✅[^lab] ✅[^20].
- **`enableOfflineQueue: false` also rejects before the first connection.** The client connects lazily, so its first command was rejected with `ERR_REDIS_CONNECTION_CLOSED Connection is closed and offline queue is disabled`; after `await client.connect()` commands worked. A command sent 20 ms after a server-side kill was rejected the same way, and one sent 500 ms later succeeded on the reconnected client ✅[^lab]. The docs say only that commands are rejected while disconnected ✅[^20].
- **Redis `onclose` and reconnects.** After a server-side `CLIENT KILL` with `autoReconnect` on, `onconnect` ran a second time and `onclose` did not run (2 runs); `onclose` ran when the retries ran out or `idleTimeout` closed the client ✅[^lab].
- The S3 and Redis clients have their own deep docs pages; this catalog records what ran against the lab servers, and those pages list every option ✅[^19] ✅[^20].
- **`Bun.cron` details** (`bunlab:2` and `oven/bun:1.4.5`) ✅[^lab]:
  - OS-level: registering the same title again replaced its line (from `0 * * * *` to `* * * * *`) instead of adding one; `@daily` was stored as `0 0 * * *`; a title with a space, an out-of-range field (`61 * * * *`) and a missing script each threw `TypeError` (`ERR_INVALID_ARG_TYPE`); `Bun.cron.remove()` of an unknown title resolved. The job ran with `cwd` `/root` and `PATH=/usr/bin:/bin`, cron's own environment, so the script should not rely on the caller's folder or `PATH`.
  - In-process errors match `setTimeout` ✅[^15]: a handler that threw, with no listener, printed `error: boom` and exited the process with code 1 at its first fire; with an `unhandledRejection` listener, a rejecting `async` handler was reported and fired again the next minute.
  - `jest.useFakeTimers()` drives in-process jobs ✅[^15]: from a fake 10:00:30, nothing fired after 29 s, one fire at 10:01:00 after 31 s, and three by 151 s.
  - `Bun.cron.parse` with `{ tz: "UTC" }`: `0` and `7` both meant Sunday; `0 0 15 * FRI` matched Friday 27 November before the 15th (either field matches); `Monday-Friday` and `@daily` parsed; `30 2 * * *` in `America/New_York` on the spring-forward day 2027-03-14 → `07:30Z`, that is 03:30 local, shifted by the missing hour as the docs say ✅[^15].
- **`Bun.WebView` differences from the docs** ✅[^21], all ✅[^lab]:
  - `evaluate()` results: the docs say they round-trip through `JSON.stringify` ✅[^21]. On macOS they did: `new Date(0)` → `"1970-01-01T00:00:00.000Z"`, `() => 1` → `undefined`, a cyclic object rejected with `JSON.stringify cannot serialize cyclic structures`. On Linux (Chrome) `new Date(0)`, `() => 1` and a `Map` all came back as `{}`, and a cyclic object rejected with `Object reference chain is too long`.   - Killing the browser with `SIGKILL` rejected the pending `evaluate` with `Chrome process closed the pipe`, not the `Chrome killed by signal 9` the docs show; later calls threw `ERR_INVALID_STATE … view is closed`.
  - On macOS the run left `~/Library/Preferences/wvmac.plist`, named after the executable, holding `WebAutomaticDashSubstitutionEnabled`, `WebAutomaticQuoteSubstitutionEnabled` and `WebAutomaticTextReplacementEnabled`, all `false`: the WebKit settings behind the docs' promise that `type()` applies no smart-quote substitution ✅[^21]. The plist ran `ProgramArguments` = the Bun binary's real path, `run`, `--cron-title=kbtest`, `--cron-period=* * * * *` and the script's absolute path, with logs at `/tmp/bun.cron.kbtest.stdout.log` and `.stderr.log`; `* * * * *` became an empty `StartCalendarInterval` dict. ## Takeaways
- Check this catalog before adding an npm dependency for hashing, globbing, semver, YAML/TOML/JSON5, compression, tar, UUIDs or colours. [rule-candidate]
- Hash passwords only with `Bun.password.hash` (argon2id by default) and compare with `Bun.password.verify`, never with `Bun.hash` or a plain SHA digest. [rule-candidate]
- Always pass a `sessionId` to both `Bun.CSRF.generate` and `Bun.CSRF.verify`. [rule-candidate]
- Expect `Bun.secrets` to fail in containers and in CI (continuous integration) runs, which seldom run an unlocked Secret Service; read secrets from the environment there.
- Always pass `region` to `S3Client` when you also pass an `endpoint` for a non-AWS server. [rule-candidate]
- With `enableOfflineQueue: false`, `await client.connect()` before the first Redis command. [rule-candidate]
- Return plain JSON-safe values from `WebView.evaluate()`, because the Chrome backend turns dates, maps and functions into `{}`. [rule-candidate]
- For golden-image tests that must match on Linux and macOS, set `Bun.Image.backend = "bun"` and use only JPEG, PNG and WebP. [rule-candidate]
- Never extract an untrusted archive with `Bun.Archive` 1.4.5 into a folder that may already hold symlinks, or read one with `files()` without a size check. [rule-candidate]
